# 역할별 기능 테스트 같이 진행

답변 형식은 프로젝트 CLAUDE.md 를 따른다. 모든 설명은 비개발자가 읽는 쉬운 말로, 마지막에 사람 몫을 모은 절(제목은 프로젝트가 정한 것 · 없으면 「👤 내 차례」).

## 0. 파일 — 기록은 프로젝트 안에 둔다

| 파일 | 위치(기본값) | 쓰임 |
|---|---|---|
| 점검표 | `_bmad-output/implementation-artifacts/role-test/CHECKLIST.md` | 역할 × 메뉴 표 · 권한 표 · 행별 「눌러 볼 것 / 보여야 하는 것」 |
| 결과(정본) | `_bmad-output/implementation-artifacts/role-test/RESULTS.md` | 답을 받을 때마다 먼저 여기에 적는다. 첫머리 「상태:」 줄 = 다음에 할 행 |

- 이 스킬 폴더에는 **틀만** 있다(`references/CHECKLIST.template.md` · `references/RESULTS.template.md`). 실제 점검표와 결과에는 주소·역할 구성·알려진 문제가 들어가므로 **스킬 폴더(공유·공개될 수 있다)에 두지 않는다.**
- 점검표가 없으면 먼저 만든다: 프로젝트의 경로·역할·메뉴 표시 규칙 코드를 읽어 역할 × 메뉴 표를 만들고, 역할마다 8~12행의 확인 항목을 적는다. 근거 파일과 줄을 함께 적는다.
- 클라우드 문서를 정본으로 삼지 않는다. 왜: 만든 계정 소유라 다른 계정·다른 창에서 열리지 않을 수 있다. 파일 하나가 유일한 원본이다.

## 1. 시작할 때 (매번)

1. 결과 파일을 **끝까지** 읽고 「상태:」 줄과 빈 결과 칸을 본다. 채워진 행은 다시 묻지 않는다.
2. 프로젝트 CLAUDE.md 에서 **연습용 주소와 운영 주소**를 읽는다. 없으면 사용자에게 묻는다 — 지어내지 않는다.
3. 연습용 주소의 배포본이 확인하려는 기능을 담고 있는지 본다(배포 기록). 없으면 그 행은 「못 해봄」 후보라고 미리 알린다.

## 2. 진행 방식 — 한 번에 조금씩, 선택지로

역할 하나씩. 한 역할 안에서:

1. **안내(3~5행 묶음)**: 로그인할 계정의 **키 이름**(예: `.env.local` 의 `QA_<역할>_*` — 로그인은 사용자가 직접, AI 는 비밀번호를 치지도 출력하지도 않는다) · **전체 주소 `https://…`**(경로만 적지 않는다) · 표(눌러 볼 것 / 보여야 하는 것). 행마다 「무엇을 보면 통과인지」 한 줄.
   - AI 가 먼저 화면을 촬영해 볼 수 있으면(`screen-check` 스킬) 그 판정을 함께 보인다. 안내는 역할·메뉴·상자 이름까지 짚는다.
2. **결과 받기 = 질문 도구(AskUserQuestion)**. 한 호출에 행 최대 4개(질문 1개 = 행 1개 · 머리말 = 행 번호). 선택지 4개 고정:
   - 「통과」 — 보여야 하는 것이 그대로 보임
   - 「문제」 — 다르게 보이거나 안 됨
   - 「못 해봄」 — 오늘 확인 못 함
   - 「정책상 정상」 — 3절 목록에 해당
   「문제」가 나오면 **바로 이어서** 6요소(역할 · 화면 · 눌렀던 것 · 기대 · 실제 · 캡처 유무)를 채울 만큼만 더 묻는다.
3. **받는 즉시 기록**: 결과·메모 칸 → 「상태:」 줄 갱신. 기록은 부분 수정 도구로 하거나, 새 내용을 다 만든 뒤 한 번에 쓴다. 왜: 파일을 먼저 비우고 쓰는 스크립트는 중간에 실패하면 원본을 0바이트로 만든다.
4. **역할 마지막 질문(필수)**: 「이 역할에서 점검표에 없던 것 중 확인하면서 알게 된 추가 수정사항이 있나요?」(없음 / 있음 — 직접 적기). 받은 내용은 그 역할의 「더 추가할 내용」 줄에 6요소로.
5. 다음 역할로.

판단이 애매한 행은 코드로 근거를 붙인다(경로 · 역할 · 메뉴 표시 규칙). DB 확인이 필요하면 **개발 DB 의 읽기 전용 조회만** 한다. 운영 DB 는 이 스킬에서 조회하지 않는다.

## 3. 정책상 정상

「메뉴가 안 보인다」「버튼이 없다」가 **의도한 권한 설계**인 경우의 목록이다. 점검표를 만들 때 프로젝트의 권한 규칙에서 뽑아 결과 파일 첫머리에 적어 두고, 해당 행은 문제로 적지 않는다(메모 = 「해당 없음 — 정책」 + 근거). 권한 구조가 바뀌는 중이면 영향받는 행을 표시해 두고, 바뀐 것이 배포될 때까지 판정하지 않는다.

## 4. 금지

- **운영 주소에서 저장·발행·초대·삭제를 지시하지 않는다.** 보기만.
- 러너의 저장소 복사본과 다른 창의 작업 폴더를 건드리지 않는다. 개발 DB 쓰기·삭제 금지(정리는 사용자의 지시 뒤 별도).
- 테스트 도중에는 스토리 파일·에픽·상태 파일을 만들지 않는다 — **전부 끝난 뒤 한 번에**(5절). 왜: 도중 등재는 같은 화면의 문제를 여러 스토리로 쪼갠다.

## 5. 전부 끝나면 (또는 「오늘은 여기까지」)

1. **전체 마무리 질문**: 「테스트 전체를 보고 더 추가할 내용이 있나요?」
2. **결정 대기 묻기**: 결과 파일 「결정 대기」 항목을 질문 도구로 한 번에(추천안을 첫 번째에 두고 표시). 권한을 넓히는 결정처럼 답이 꼭 필요한 것은 답 없이 등재하지 않는다.
3. **분류표**: 문제 줄 + 추가 내용 + 역할 밖 발견 전건을 「해당 없음(정책) / 진짜 결함」으로 가르고, 진짜 결함은 **화면별로 묶어** 제안 스토리 번호를 붙인다(번호는 에픽 문서와 상태 파일에서 최대 번호를 다시 확인).
4. **후속 스토리 한 번에 등재**:
   - 에픽 문서에 스토리 항목(사용자 이야기 · 인수 조건 · 근거 = 결과 파일 행 번호 · 사용자 결정) 추가 + 상태 파일에 `backlog`. 스토리 파일은 러너의 작성 단계가 만든다.
   - 보안·권한이 걸린 묶음은 인수 조건에 「이월 금지 · 변경 기록 남김」을 적는다.
   - **러너가 도는 동안에는 러너 폴더와 기준 갈래에 직접 쓰지 않는다.** 등재는 `batch-24-multiAG/ops/gap-apply.sh`(라운드 경계 적용)로 하거나 러너가 쉬는 틈에 한다. 적용 조각은 사본에서 먼저 검산한다.
   - 갈래 이름에 러너 체인보다 미래 날짜를 쓰지 않는다. 왜: 러너가 그 갈래를 자기 체인으로 오인해 멈춘다.
   - 등재 뒤 편성 미리 보기를 러너 폴더에서 돌리지 않는다(엔진 장부를 더럽힌다). 다음 슬롯의 일지에서 새 스토리가 편성됐는지만 본다.
5. **마무리 보고**: 역할별 통과·문제·못 해봄 수 표 · 문제 몇 건 · 등재한 스토리 목록 · 러너 편성 확인 결과 + 사람 몫(남은 결정 · 개발 DB 정리 승인).

## 6. 고친 뒤 다시 보기

러너가 고친 것이 연습용 또는 운영에 반영되면, 결과 파일의 「문제」 행만 골라 같은 방식으로 다시 확인한다. 통과하면 메모에 「고침 확인(날짜 · 어느 스토리)」을 적는다 — 문제 줄을 지우지 않는다.
